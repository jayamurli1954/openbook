# ADR-0035: Phase 1 — Structure Studio Architecture

- **Status:** Accepted; implementation requires separate explicit authorization
- **Date:** 2026-09-27
- **Phase:** ROADMAP Phase 1 — MVP Guided Book Creation (§3.4)
- **Area:** Desktop / Product Surface / Structure Studio
- **Depends on:** ADR-0006, ADR-0014, ADR-0016, ADR-0019, ADR-0029, ADR-0031, ADR-0033, ADR-0034
- **Supersedes:** None
- **Selection record:** `docs/PHASE-1-STRUCTURE-STUDIO-SELECTION.md`
- **Implementation authorization:** None. This ADR accepts architecture only.

## 1. Context

OpenBook has closed ADR-0033 Guided Start and ADR-0034 Writing Studio. The desktop already provides:

- a canonical Book with `frontMatter`, `chapters`, and `backMatter` (ADR-0006);
- `BookSession` structure operations: add, remove, reorder, move between matter, title, and role, including fail-closed rejection of deleting or moving the last main-matter chapter;
- section roles that must be valid for the target matter;
- `DesktopStudioCoordinator` as the studio authority;
- ADR-0029 package Save/Open and ADR-0031 autosave;
- EPUB `nav.xhtml` generated by the publishing engine from Book structure (ADR-0009), not from a second stored outline.

ROADMAP §3.4 Structure Studio requires:

- front matter;
- main matter;
- back matter;
- chapter ordering;
- section hierarchy;
- automatic navigation structure.

**Gap:** `EditorSurface` lists main-matter chapters only. Authors cannot see or arrange front and back matter as a product surface. Navigation is already derived at publish time; the studio does not yet show that order as structure chrome.

**Hierarchy limit:** the Book Model stores a flat list of sections inside each matter kind. Heading blocks live inside a section. A nested section tree is not representable without a separate Book Model ADR. Structure Studio must not invent one.

## 2. Decision

OpenBook will implement Phase 1 Structure Studio as a **desktop structure-surface architecture** that:

1. Productizes arrangement of existing Book sections after Writing Studio.
2. Keeps **Book Model + BookSession + DesktopStudioCoordinator** authoritative.
3. Uses only structure operations the Book Model and `BookSession` already support.
4. Treats navigation as a **read-only projection** of Book section order. EPUB `nav.xhtml` remains a publishing-engine output.
5. Reuses ADR-0031 autosave and ADR-0029 package binding.
6. Remains **AI-optional**. Outline generation is out of scope.

```text
React Structure Studio UI (matter groups, order, role, nav preview)
        |
        v
Structure ports (list / add / rename / reorder / move / remove / role)
        |
        v
DesktopStudioCoordinator / BookSession
        |
        v
Book Model (frontMatter, chapters, backMatter) — canonical
        |
        +--> ADR-0031 autosave / ADR-0029 package
        +--> EPUB nav.xhtml (publish time; not a stored studio document)
```

### 2.1 Existing coordinators remain authoritative

Structure Studio must not:

- write EPUB/PDF/HTML or `nav.xhtml` itself;
- store a parallel TOC, outline, or TipTap document;
- bypass `BookSession` validation / rollback;
- delete or move the last main-matter chapter;
- assign a role that is invalid for the target matter;
- invent a second autosave or package protocol;
- silently invent sections when a structure operation fails.

### 2.2 Capability mapping (MVP)

| ROADMAP §3.4 capability | Architecture position |
|---|---|
| Front matter | `book.frontMatter` via `BookSession.addSection` / `moveSection` (`matter: "front"`) |
| Main matter | `book.chapters`; last chapter cannot be removed or moved out |
| Back matter | `book.backMatter` via the same session operations |
| Chapter ordering | `reorderSection` within one matter kind |
| Section hierarchy | Flat sections per matter, plus heading blocks inside a section. Nested section trees are **deferred** pending a Book Model ADR |
| Automatic navigation structure | Read-only projection of section order (title, matter, role). Publishing keeps ADR-0009 `nav.xhtml` generation |

### 2.3 Host vs UI boundary

- React UI: three matter groups, add/rename/reorder/move/remove, role display, empty-matter copy, read-only nav preview.
- Domain: `BookSession` and `DesktopStudioCoordinator` remain the mutation authority.
- Writing Studio remains the text editor. Structure Studio does not replace TipTap authoring.

### 2.4 Explicit non-goals for this ADR

- Design Studio / Metadata Wizard / Cover Wizard (later Phase 1 ADRs)
- Nested section trees or basic tables (pending model ADRs)
- AI outline generation
- Hand-edited EPUB navigation documents
- DTP page layout
- Code signing / multi-OS packaging
- Changing Gate 10 packaging verification semantics

## 3. Implementation sequencing (not authorized here)

When separately authorized, implementation should proceed in small slices, for example:

1. **Slice 1 — Structure contract:** capability matrix + ports for list/add/rename/reorder/move/remove/role; fail-closed last-chapter and invalid-role results; tests; no chrome.
2. **Slice 2 — Matter rail:** front/main/back groups, add, rename, reorder within a matter.
3. **Slice 3 — Move and role:** move between matters; role constrained to the target matter; last main chapter stays fail-closed.
4. **Slice 4 — Navigation preview:** read-only order projection from the Book; no stored TOC.
5. **Slice 5 — Hardening:** empty-matter copy, EN+KN titles through package Save/Open, regression guard that no parallel outline is persisted.

Exact slice boundaries may be adjusted in per-slice proposals; each slice still needs explicit authorization.

## 4. Testable architectural invariants

1. Every structure edit yields a Book Model–valid Book, or a structured fail-closed error.
2. The last main-matter chapter cannot be deleted or moved out of main matter.
3. A section role must be valid for its matter kind.
4. Navigation preview and EPUB nav are projections of Book order, never a second stored document.
5. Autosave continues to use ADR-0031 package Save semantics when a package root is bound.
6. No AI dependency is introduced by this ADR’s slices.
7. Nested section trees and tables are not shipped under this ADR alone.

## 5. Consequences

### Positive

- Gives Phase 1 a structure surface without a new document model.
- Reuses `BookSession` rules that already protect the last chapter and role/matter pairing.

### Trade-offs

- “Section hierarchy” in the roadmap is flatter than a nested tree until a model ADR exists.
- Writing Studio’s chapter rail may coexist with Structure Studio until a later shell cleanup.

## 6. Non-authorizations

This ADR does **not** authorize implementation, dependency changes, UI chrome delivery, Book Model schema changes, AI features, or any Phase 1 Structure Studio slice until a maintainer issues an explicit slice authorization.
